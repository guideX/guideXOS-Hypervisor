guideXOS Hypervisor — Phase RISCV-8 Report
=========================================

transactionally loads PT_LOAD ranges, and an independently linked RV64IMA

Supported ELF profile and validation
------------------------------------

- Added include/riscv/riscv_elf64_loader.h and
  src/riscv/riscv_elf64_loader.cpp. The accepted profile is ELF64,
  little-endian, current ELF version, System V or GNU OS ABI with ABI version
  zero, EM_RISCV, ET_EXEC, e_flags zero (RV64IMA soft-float), and nonempty
  PT_LOAD segments.
- Checks full ELF magic, class/data/version, e_type/e_machine/e_flags, ELF
  header size 64, program-header entry size 56, program-header offset/count/
  extent, every file-backed range, and referenced section-table extent when
  present. Section headers can be absent and never control memory placement.
- Rejects extended or empty program-header numbering, more than 64 headers,
  files above 16 MiB, more than 16 PT_LOAD segments, or more than 8 MiB total
  segment memory. This bounds parser work and staging/rollback allocations.
- Rejects ELF32, big-endian, ET_REL, ET_DYN/PIE, wrong architecture, RVC,
  floating-point ABI, RVE, TSO, unknown ELF flags, PT_INTERP, PT_DYNAMIC,
  runtime dependencies/relocations, PT_TLS, PT_SHLIB, executable stacks,
  unknown program-header types, and unsupported alignments.
- For each PT_LOAD, validates p_filesz <= p_memsz, file and destination bounds,
  address overflow, p_align power-of-two and file-offset/address congruence,
  and p_paddr == p_vaddr. It rejects overlaps, reserved guest regions, and
  CPU timer MMIO. Entry must be four-byte aligned and inside file-backed
  executable PT_LOAD bytes.
- Placement is fixed identity mapping: p_vaddr is the execution address;
  p_paddr must equal p_vaddr. There is no rebasing, ET_DYN, relocation, or
  page-table translation. PT_LOAD flags are validated and used to validate
  the entry; the CPU does not enforce per-segment R/W/X permissions.
- The loader builds the full load plan before memory changes, stages exact
  file bytes plus zero-filled BSS and snapshots of all destination ranges,
  then writes only PT_LOAD ranges. A write failure restores the attempted and
  prior ranges. The CPU is reset to M-mode and PC is set from e_entry only
  after all writes succeed. Invalid input tests compare the entire RAM image,
  PC, privilege, GPR, CSR, step count, and retired count before/after.
- Loader errors distinguish invalid ELF format, unsupported architecture or
  ABI/type, malformed program headers, invalid segment bounds, overlap,
  insufficient RAM, reserved collision, runtime-linking requirements,
  relocations, invalid entry, resource limits, and guest-memory access.

Guest RAM and execution contract
-------------------------------

- Guest RAM: [0x80000000, 0x81000000), 16 MiB. CPU boot state is one hart
  (mhartid 0), M-mode, PC from ELF e_entry, satp Bare, and the existing CPU
  reset CSR state. ELF loading does not perform the privilege transition.
- Guest-owned stack reservation: [0x80FFF000, 0x81000000), initialized by
  guest instructions with SP=0x80FFFFF0.
- Guest output and signature reservation: [0x80010000, 0x80011000). The exact
  message is written at 0x80010000. A version-1 signature begins at
  0x80010100; its completion word is at offset 112 and is the final guest
  store. Host trap-record reservation: [0x80011000, 0x80012000).
- The M-mode ELF entry installs mtvec, prepares mepc and mstatus.MPP=S, and
  executes MRET. The test observes M-mode execution before this handoff and
  S-mode execution afterward. The guest SBI Base ECALL traps architecturally
  to M-mode; the guest trap handler advances mepc and executes a second MRET.
- The loader itself exposes the intended PT_LOAD addresses and sizes. The
  integration test starts RAM with a sentinel pattern, checks each loaded
  file range against the original ELF bytes, verifies the 16-byte BSS tail is
  zero, confirms noncontiguous gaps remain unchanged, and checks reserved
  output/trap/stack memory.
- The previous raw-binary entry 0x80000000 differs from the ELF e_entry
  0x80200000. The harness confirms the first CPU step begins at the ELF entry.
- Guest instruction budget: 2,000 CPU steps. The harness also executes an
  eight-step prefix and confirms the completion word remains clear.

Boot readiness and recommended RISCV-9
--------------------------------------

Selected next external target: the OpenSBI generic FW_JUMP M-mode firmware
on a single-hart QEMU virt-compatible profile, then a freestanding S-mode
payload. OpenSBI documents RV64IMA_Zicsr, S-mode, and direct mtvec as its base
platform minimum; these match the CPU's selected execution profile. This is
still a new external firmware execution target: the existing host SBI provider
does not execute OpenSBI code. Start with FDT handoff and the serial/timer
devices needed by the selected generic platform build. Do not attempt Linux in
RISCV-9.

Remaining requirements, separated by guest:

- OpenSBI firmware: load a genuine M-mode firmware image, provide hart ID and
  an 8-byte-aligned FDT address in a0/a1, and implement the platform services
  the chosen firmware build discovers. There is no FDT generator or authentic
  firmware handoff yet. A single-hart target avoids secondary-hart HSM/IPI
  startup but still needs the selected firmware's timer and console path.
- Compressed instructions: RV64C is not executed or advertised. It is not part
  of OpenSBI's stated base minimum, so RISCV-9 can use an rv64ima_zicsr build.
  Any default external Linux or firmware artifact must be inspected for its
  actual ISA requirements or built to the emulator's supported ISA; standard
  RV64GC output may require RV64C execution.
- Device tree and memory: QEMU virt normally supplies an FDT describing
  addresses, interrupts, RAM and devices. The current 16 MiB test RAM and
  reservations are a fixture profile, not a Linux map. A later Linux boot
  needs consistent RAM, FDT, firmware, kernel, optional initramfs and
  reserved-memory regions.
- Console and device MMIO: there is no NS16550 UART or serial dispatch, full
  CLINT/ACLINT model, PLIC/APLIC/IMSIC, or virtio. The CPU only models its
  narrow single-hart mtime/mtimecmp registers. A QEMU virt Linux console and
  external device interrupts require compatible devices and FDT nodes.
- SBI and hart services: the current boundary supplies SBI Base and TIME but
  is host-side test firmware. Linux probes TIME/IPI/RFENCE and may use SRST
  and DBCN; SMP ordered boot/hotplug uses HSM. Single-hart OpenSBI boot does
  not require starting secondary harts; Linux SMP remains blocked on
  inter-hart interrupt, remote-fence and HSM behavior.
- PMP and isolation: PMP is optional in OpenSBI's base platform requirements,
  but without PMP OpenSBI cannot protect M-mode firmware or reserved regions.
  Linux's direct map must exclude resident firmware/protected memory through
  its FDT or UEFI memory description.
- Linux image contract: the documented Linux handoff uses a0=hartid,
  a1=FDT, satp=0, and a 2 MiB RV64 kernel placement boundary. The standard
  QEMU virt/OpenSBI Linux artifact is arch/riscv/boot/Image, a flattened image,
  not vmlinux ELF. RISCV-8's ET_EXEC loader does not replace a Linux Image
  loader, initrd placement, FDT generation, or full OS boot protocol.
