Firmware-to-supervisor handoff
------------------------------
OpenSBI starts at 0x80000000 in M-mode. The observed handoff enters S-mode at
0x80200000 with a0=0, a1=0x82200000, and satp=0 (Bare). The guest deliberately
enables Sv39 later; the later observed satp is 0x8000000000083c00 (MODE=8).
The supervisor entry is 2 MiB aligned. The accepted standalone supervisor ELF
is a fixture, not a Linux Image.

FDT audit and resolution of the RISCV-16 discrepancy
----------------------------------------------------
RISCV-16 used the nonstandard property name riscv,mmu-type. OpenSBI v1.8.1
looks for the standard mmu-type property during CPU fixup; when it is absent,
the CPU node is disabled. Its domain fixup removes opensbi-domain only from
enabled CPU nodes. This explains the earlier disabled node and retained
assignment property; it was not required by the restricted-domain policy.

The fixture now declares mmu-type = "riscv,sv39". With unchanged upstream
OpenSBI and an authentic guest-executed boot, the post-fixup FDT contains
exactly one enabled hart 0 node, advertises RV64IMA_Zicsr and Sv39, and has no
opensbi-domain property. The observed CPU description is suitable for
single-hart supervisor discovery. OpenSBI source references:
https://raw.githubusercontent.com/riscv-software-src/opensbi/74434f255873d74e56cc50aa762d1caf24c099f8/lib/utils/fdt/fdt_fixup.c
https://raw.githubusercontent.com/riscv-software-src/opensbi/74434f255873d74e56cc50aa762d1caf24c099f8/lib/utils/fdt/fdt_domain.c

Final FDT validation also matches:
- RAM 0x80000000-0x84000000 and 10 MHz timer frequency.
- UART0 0x10000000-0x10000100, PLIC source 10.
- UART1 0x1000a000-0x1000a100, PLIC source 12.
- PLIC 0x0c000000-0x0c400000, 96 sources, exposed S context

Memory inventory and reservations
---------------------------------
Physical RAM is 0x80000000-0x84000000. OpenSBI reserves its protected text
0x80000000-0x80080000 and data/scratch 0x80080000-0x800a0000 as no-map.
The fixture reserves the unused tail of the 2 MiB firmware slot,
0x800a0000-0x80200000, to keep a supervisor memory allocator away from an
unmatched S/U PMP hole.

The remaining explicit no-map reservations are:
- Supervisor test payload: 0x80200000-0x80220000.
- Firmware FDT and post-fixup allocation: 0x82200000-0x82203000.
- Guest page tables: 0x83c00000-0x83c04000.
- Guest result records: 0x83e00000-0x83e01000.
- Guest stack: 0x83ff0000-0x84000000.

The supervisor ELF has separate PT_LOAD segments at
0x80200000-0x802006ec (RX), 0x802006f0-0x80200825 (R), and
0x83c00000-0x83c04000 (R). Its 0x80200000-0x83c04000 address envelope is
not a contiguous image; validation checks each real segment against its own
reservation and against the FDT, result, and stack. Every reservation is
nonzero, overflow-safe, within RAM, and pairwise disjoint except for declared
containment by RAM/PMP permission windows. The 12 KiB FDT capacity contains
the actual 8,437-byte fixed-up FDT.

Reservations for payload, page tables, result data, and stack are specific to
this focused guest. They are not proposed as the long-term reservation policy
for a Linux executable image. The firmware slot tail remains no-map because
it is outside the domain's S/U grants.

Locked PMP transitions and reset recovery
------------------------------------------
The independent RV64IMA_Zicsr guest uses M-mode CSR instructions; no host-side
PMP mutation substitutes for the guest writes. The existing unlocked policy
test retains deny -> grant -> allowed -> revoke -> deny behavior.

In the locked run, entry 1 is locked NAPOT for 0x80010000-0x80010008. M-mode
attempts to change pmpaddr1 and pmpcfg0; readback and the actual PMP trace show
the values are retained. Entry 4 is locked TOR for 0x80011000-0x80011008.
Its OFF predecessor entry 3 retains pmpaddr3 because entry 4 is locked.
Two real S-mode loads fault with cause 5 at those exact ranges. Unrelated PMP
entries remain unchanged and the CPU records no MMIO side effects.

The production CPU reset path clears all 16 entries and their addresses while
preserving guest RAM and the phase word. The same guest restarts, configures
the same NAPOT region unlocked, changes its address and permission through
actual M-mode CSR writes, executes S-mode access successfully, and records the
expected value. Evidence: locked run 146 steps / two traps; reset recovery
82 steps / zero traps; two genuine M-mode SFENCE.VMA instructions. The MMU
does not cache translations; no TLB invalidation effect is claimed.

Limits and RISCV-18 recommendation
---------------------------------
This phase establishes a single-hart, physical-access and boot-description
contract; it does not establish a complete hypervisor or secure virtualization
boundary. The PLIC window is the full 4 MiB aperture; standard PMP leaves
unlocked M-mode access intact; there is no TLB; and the no-map payload, result,
stack, and page-table reservations are test-fixture allocations.

Recommended RISCV-18: add a pinned non-UEFI Linux Image placement/entry
contract using the existing single-hart memory/device profile. Validate the
Image's real extents, reserved-memory interaction, a0/a1, Bare satp, and S-mode
entry first; keep SMP, SBI IPI/HSM/RFENCE, new hardware, and Linux peripheral
enablement out until the existing UART, PLIC, timer, and domain contract has
been extended deliberately.
