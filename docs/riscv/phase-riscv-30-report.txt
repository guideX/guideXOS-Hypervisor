guideXOS Hypervisor — Phase RISCV-30 Report
Authentic Linux serial input, U-mode command processing, and console response
Date: 2026-11-21 (America/Los_Angeles)

RESULT
------
Outcome A — authentic bidirectional Linux userspace console.

The pinned Linux v6.12 and OpenSBI v1.8.1 booted unchanged under the existing
RV64IMA_Zicsr, Sv39, one-hart, StandardPmp16 machine profile. Linux launched a
deterministic static `/init` as PID 1 in U-mode. The process opened `/dev/ttyS0`,
waited in Linux's default canonical N_TTY `read`, received five complete lines
from 41 externally injected UART0 bytes, interpreted each line in U-mode, and
sent five corresponding responses through Linux `write` and the existing UART0
transmitter. `quit` returned from `sched_yield`; PID 1 remained alive in U-mode.

The corrected Debug and Release guest evidence is byte-identical across all 13
phase-30 evidence files. No host-side command handling, task-memory write,
TTY-buffer injection, synthetic syscall return, host SBI provider, Linux
rebuild, production emulator correction, or QEMU run was used.

7. Production UART receiver audit
---------------------------------
The production receiver retains a single pending byte. The controller used
`RV64CPU::injectMachineUartReceiveByte` one byte at a time; it did not submit
an entire command while RBR was occupied and did not change the UART model.
Each next injection waited for guest execution to consume the previous byte
from UART0 RBR. Existing LSR data-ready/overrun state, IER/IIR behavior, PLIC
source routing, RBR clearing, transmitter-empty behavior, and UART1 isolation
were retained.

8. Linux TTY configuration and behavior
---------------------------------------
The fixture makes no ioctl call. It uses Linux v6.12's default N_TTY canonical
mode and echo behavior. A read was observed pending in `n_tty_read` before
input; scheduler transitions during those reads are recorded. A newline
committed each canonical line and woke the blocked read. TTY echo is separated
from userspace prompt/response writes in the console evidence. Linux's normal
newline-to-CRLF console translation is reflected in transmitted byte counts.

The source audit is recorded in
`E:\CodexArtifacts\guideXOS_Hypervisor\phase-riscv30-artifacts\riscv30-linux-source-analysis.txt`.
It covers the pinned UAPI syscall numbers, `serial8250_read_char`,
`serial8250_rx_chars`, `serial8250_handle_irq`, flip-buffer work, canonical
line commit/wake, `n_tty_read`, and `tty_read`/`copy_to_iter`.

9. External input and pacing
----------------------------
Stimulus lines were `ping\n`, `status\n`, `echo hello\n`,
`unrecognized\n`, and `quit\n`: 41 bytes total. All 41 were accepted; 0 were
rejected. For each byte, the controller recorded guest retirement/PC,
privilege, receiver-ready state, PLIC source state, injection result, and the
later receiver-consumption sequence. It waited on observed U-mode read and
Linux scheduling state, used no wall-clock sleep as a readiness substitute,
and injected no command into RAM, task memory, or the TTY layer.

10. UART RX, PLIC, and TTY evidence
----------------------------------
All 41 injections observed receiver-ready after injection and PLIC source-10
assertion; all 41 were later consumed by UART0 RBR reads. A byte-for-byte
cross-check matched every stimulus consume sequence and value to the
production UART MMIO trace. There were 43 total RBR reads: the 41 injected
characters and two zero-valued no-data reads by the Linux driver. The run
observed 27 supervisor external IRQ deliveries, 27 source-10 PLIC claim reads,
and 27 completion writes. Every claim was completed. RX overrun observations
and rejected injections were both zero. Linux's driver reads LSR/IIR while
servicing the receive path: 7,440 LSR reads and 58 IIR reads were recorded.
The event trace retains those MMIO operations.

11. Real Linux syscall evidence
-------------------------------
Linux UAPI numbers were verified from the pinned source: `getpid` 172,
`openat` 56, `read` 63, `write` 64, and `sched_yield` 124. All 18 captured
syscalls were genuine U-mode ECALLs delivered to S-mode and returned to U-mode
through SRET.

- `getpid()` returned 1.
- `openat(AT_FDCWD=-100, "/dev/ttyS0", O_RDWR=2)` returned fd 3.
- Five `read(fd=3, length=64)` calls returned 5, 7, 11, 13, and 5 bytes.
- Ten writes returned the five prompt and five response buffers.
- The final `sched_yield()` returned 0.

Caller PC, dispatch PC/symbol, arguments, return value, SRET PC, return PC,
and buffer evidence are in `riscv30-user-syscalls.json` and
`riscv30-tty-read-evidence.json` for each configuration.

13. U-mode command parsing

The parser's U-mode instruction PCs were 0x101d8 (`ping`), 0x101e8 (`status`),

All five expected branch instructions were observed executing in U-mode.
Input bytes, parser labels, response buffers, write syscalls, and TX matches
are in `riscv30-command-events.json`.

14. Guest-generated responses and console provenance
----------------------------------------------------
The guest selected these response buffers and Linux transmitted each through
UART0 TX MMIO:

- `ping` -> `pong\n` (5 user bytes; 6 UART bytes after CRLF translation).
- `status` -> `status:pid=1\n` (13 user bytes; 14 UART bytes).
- `echo hello` -> `hello\n` (6 user bytes; 7 UART bytes).
- `unrecognized` -> `unknown command\n` (16 user bytes; 17 UART bytes).
- `quit` -> `quit acknowledged\n` (18 user bytes; 19 UART bytes).

The five prompts account for 50 userspace bytes. Responses account for 58
userspace bytes and 63 UART bytes; all 113 userspace UART bytes were matched
to genuine Linux write buffers and guest MMIO TX writes. TTY echo accounts for
46 distinct bytes and was observed for all five lines. The 11,965-byte console
contains 4,356 OpenSBI pre-handoff bytes and 7,609 Linux S-mode bytes; UART1
output was 0. After separating user writes and echo, 7,450 bytes remain
classified as kernel/other S-mode console text; this harness does not further
split printk from other S-mode output. See `riscv30-console-analysis.json`
and `riscv30-console.bin`.
