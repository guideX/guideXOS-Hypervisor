Authentic Linux execve and process identity
------------------------------------------
PID 1 entered the independent /init ELF at 0x10000. It used Linux getpid,
opened /dev/ttyS0, wrote its marker, initialized private memory, and invoked
clone(SIGCHLD) with flags 17. Linux returned child PID 21 to PID 1 and zero
to the child. The existing COW checks still passed: child value
0x55667788, parent value 0x11223344 after wait.

Before exec, PID 21 executed /init U-mode bytes, checked getpid=21 and
getppid=1, and wrote its distinct pre-exec marker. It issued the genuine
Linux RISC-V execve syscall:

  syscall: 221; U-mode ECALL PC: 0x101e0
  path: /bin/child; pathname pointer: 0x1020b
  argv pointer: 0x10216; envp pointer: 0x1022e
  argv: ["/bin/child", "execve-riscv28"]
  envp: ["GUIDEXOS_RISCV28=present"]
  dispatch: __riscv_sys_execve at 0xffffffff80214580

The pointers and strings were read from mapped guest U-mode memory. Linux's
child-specific bprm_execve, begin_new_exec, setup_arg_pages, and start_thread
events were captured. Successful exec replaced the image at entry 0x20000;
the first retired instruction 0x00010413 matches the child ELF PT_LOAD bytes.
PID 21, parent PID 1, and task pointer 0xffffffd6018e6780 were preserved.
The task's satp root changed during exec, but satp was not used as the sole
image-identity proof. The old continuation at 0x101e4 was not resumed.
The new image retired 406 U-mode instructions.

At the new ELF entry, sp was 16-byte aligned. The Linux RISC-V entry ABI was
verified as sp -> argc, argv pointers, NULL, envp pointers, NULL, auxv.
The guest child inspected argc=2, both argv strings, the environment token,
and both null terminators using read-only production Sv39 translation.
The guest validation site was reached and passed.

The post-exec child called getpid (21), getppid (1), opened its own
/dev/ttyS0 descriptor (fd 4), and wrote its marker. The write(64) returned
46 bytes; the UART recorded 47 bytes because Linux's tty path expands the
newline to CRLF. The child then called exit(42), entered Linux do_exit, and
retired no further U-mode instructions. Parent wait4 returned PID 21 and
copied status 10752 (42 << 8) to guest address 0x11008. A subsequent
wait4(-1, ..., WNOHANG, ...) returned -ECHILD. PID 1 emitted its success
marker and continued with getpid/sched_yield.

Userspace markers were attributed to actual syscalls and UART0 MMIO:
  PID 1:   "guideXOS RISCV-28: parent initialized\n" (38-byte write)
  PID 21:  "guideXOS RISCV-28: child before exec\n" (37-byte write)
  PID 21:  "guideXOS RISCV-28: new ELF argv/env ok pid=21\n" (46-byte write)
  PID 1:   "guideXOS RISCV-28: parent reaped status=42\n" (43-byte write)
All four writes had matched guest UART0 MMIO provenance. Their UART byte
counts were respectively 39, 38, 47, and 44 after CRLF expansion. Linux
printk and firmware output remain separately attributed.

Scheduling proof includes a switch from PID 1 to the live PID 21 while the
parent wait4 was active (retirement 86,810,282), with tp changing from the
parent task pointer to the child task pointer and the kernel stacks changing.
Linux later switched back to PID 1 after child completion and reaping.

Page-walk sampler investigation
-------------------------------
The former auxiliary sampler's zero root PTE was a timing snapshot before
the first successful U-mode fetch, not evidence of a translation failure.
The audit uses Sv39Mmu::inspectPageWalk and the production
inspectTranslationReadOnly path. Both use the existing production walker;
the read-only translation disables A/D writes. The direct root-PTE probe is
readable and agrees with the production walk. The diagnostic records the
same task, VA, satp, privilege, and PC as the actual CPU step.

  /init: PID 1, VA 0x10000, satp 0x8000000000082474, root table 0x82474000,
    VPN [0,0,16]. The initial root PTE at 0x82474000 was readable zero and
    translation failed. U-mode instruction-page fault cause 12 had PC/tval
    0x10000. Linux do_page_fault (0xffffffff80670a44) and handle_mm_fault
    (0xffffffff801a1e3c) executed for PID 1. The retry walk traversed all
    three levels and translated to 0x82fe0000; its executable leaf PTE was
    0x20bf805b. The CPU then retired 0x0ac00893, matching /init.
  /bin/child: PID 21, VA 0x20000, satp 0x8000000000082483, root table
    0x82483000. The initial root PTE was readable zero. U-mode instruction
    page fault cause 12 had PC/tval 0x20000. The same child task entered
    do_page_fault and handle_mm_fault. The retry walk traversed all levels
    and translated to 0x81407000; its executable leaf PTE was 0x20501c5b.
    The CPU then retired 0x00010413, matching /bin/child.

For /init, the captured fault was at retirement 86,656,985; do_page_fault
and handle_mm_fault were observed at 86,657,047 and 86,657,360. For the new
child entry, the fault was at 86,973,710 and the handlers at 86,973,772 and
86,974,085. Thus both pre-fault zero snapshots are explained by Linux's
fault-driven mapping before successful fetch. The CPU uses an uncached
walker; no TLB behavior or invalidation semantics are claimed. No MMU repair
was required, and no translation inconsistency remains in these two cases.
