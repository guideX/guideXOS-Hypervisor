Dual UART implementation
------------------------
The CPU now owns two independent UART state instances per RV64CPU. UART0
preserves its 0x10000000 mapping and console stream. UART1 defaults to
0x1000A000 and has its own RX byte, DR/OE state, IER, IIR result, LCR/DLAB,
divisors, scratch and modem registers, TX output, reset behavior and host input
boundary. A UART1 RBR read, reset, overrun or IER update cannot alter UART0.
Two CPU/VM instances also keep both UART states and PLIC state isolated.

Each enabled UART owns one eight-byte implemented MMIO window within its
declared 0x100-byte FDT region. Byte register accesses retain the RISCV-11
fault policy; invalid widths and offsets fail rather than reaching guest RAM.
Timer, PLIC and UART overlap checks include both mappings. Firmware and guest
console writes at UART0 continue to use the UART0 output buffer.

PLIC source and arbitration behavior
------------------------------------
  UART0: 0x10000000 -> PLIC source 10
  UART1: 0x1000A000 -> PLIC source 12
  PLIC:  0x0C000000, 96 sources, hart 0 M/S contexts 0/1

The existing priority, context-enable, threshold, pending, claim and
completion implementation now receives independently asserted source 10 and
12 lines from the two UART states. Arbitration selects the highest eligible
priority; equal nonzero priorities select the lower source ID. Priority zero,
an unset context-enable bit, or priority less than or equal to threshold
blocks eligibility without discarding the UART byte or controller pending
state. Priority, enable and threshold writes immediately affect the derived
context output. A claim clears and owns only one source. Valid completion
releases only that source; an asserted level re-pends it. Invalid or unclaimed
completion leaves controller state unchanged.

The focused target covers both priority orders, equal-priority ID tie-break,
priority-zero suppression, a priority change while pending, IER masking,
source-enable masking, threshold masking, RBR isolation, claim/completion
isolation, no eligible claim returning zero, level re-pending, invalid MMIO,
reset, and two-VM isolation. The guest separately verifies local SEIE and
global SIE gating. PLIC output continues to derive from controller state; UART
injection does not write SEIP.

script verifies and reuses the pinned OpenSBI bytes; it does not fetch, patch,
or rebuild OpenSBI. The DTB retains the accepted CPU, 64 MiB RAM, 10 MHz

layout.

UART1 is declared as `ns16550a`, `ns16550` at 0x1000A000 with a 0x100-byte
register range, `reg-shift = <0>`, `reg-io-width = <1>`, 3.6864 MHz clock,
115200 current speed, the existing PLIC phandle and interrupt 12. UART0 keeps
the same properties and interrupt 10. `/chosen/stdout-path` remains
`/soc/serial@10000000`.

The independently parsed DTB passed structural and contract checks. Authentic
OpenSBI v1.8.1 executed from the reused FW_JUMP binary and initialized PLIC
MMIO. The S-mode guest executed with Sv39 enabled, accessed both UARTs and PLIC
registers through the production translation and MMIO path, handled
supervisor external cause 9, and returned through SRET. No host SBI provider
was installed in the firmware proof.

Simultaneous-pending scenarios and guest log
--------------------------------------------
The guest created five independently driven pairs. Before the first claim of
each pair, the host observed both PLIC pending bits set while S-mode global
SIE was clear; the guest also read the pending bitmap and stored a preclaim
snapshot in guest RAM. The trace captures injection destination, byte, each
UART's DR/IRQ state, source 10/12 pending, priority, threshold, SEIP transition,
trap/scause, claim, matching UART IIR/RBR read, completion, SRET, guest-log
count and final completion marker.

The guest's verified event log (source ID : received byte) is:
  12 : 0x61    10 : 0x41
  10 : 0x42    12 : 0x62
  10 : 0x43    12 : 0x63
  12 : 0x64    10 : 0x44
  12 : 0x65    10 : 0x45

Scenario A set priorities 10=1 and 12=3; source 12 was claimed first.
Scenario B reversed the priorities; source 10 was claimed first. Scenario C
used equal priority 2 and the lower source ID 10 won. Scenario D set
priorities 10=1/12=3 and threshold 2: source 12 was serviced while source 10
and UART0's original byte remained pending/data-ready. The guest lowered the
threshold and received that same UART0 byte without another host injection.
This also proves that reading UART1 does not acknowledge UART0. Scenario E
kept local SEIE clear while both sources were pending, observed sip.SEIP, then
enabled local and global delivery and serviced both requests. Four eligible
phases entered WFI with global SIE masked and woke on PLIC output.

Across the run, the S-mode handler performed ten claims, ten corresponding
UART reads, ten completions and ten SRETs. The log records five simultaneous
pending snapshots and ten source/byte records. The guest emitted:
  Hello from dual UART IRQ on guideXOS
UART0 contained 2,800 output bytes including OpenSBI console output and the
guest message. UART1 output remained empty. The guest wrote a version-12
completion signature and wrote its completion word last.

Remaining platform and OS limitations
--------------------------------------
This is a bounded single-hart PLIC/UART platform profile, not complete QEMU
virt compatibility. It does not implement Linux or U-Boot boot, SMP, PMP,
APLIC/IMSIC, virtio, PCI, storage, networking, or full NS16550 FIFO/modem
behavior. A future Linux attempt still needs an explicit kernel/firmware ISA
contract, Linux Image loading and entry state, adequate RAM/reservations, and
the devices and interrupt model required by the selected console and root
filesystem.
