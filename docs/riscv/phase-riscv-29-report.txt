First child: successful execve and reap
---------------------------------------
PID 1 entered /init at 0x10000 and created PID 21 with clone flags 17
(SIGCHLD). Linux returned the positive child PID to PID 1 and zero to PID 21.
The child verified getpid=21 and getppid=1, wrote its pre-exec marker, then
issued Linux syscall 221 with the guest pathname /bin/child, argv
["/bin/child", "execve-riscv29"], and envp ["GUIDEXOS_RISCV29=present"].
Linux dispatched __riscv_sys_execve and entered the separate ELF at 0x20000
while preserving PID 21 and parent PID 1. The child ELF verified its Linux
argc/argv/environment stack, performed its success write, and exited with 42.
PID 1 collected wait status 10752 (42 << 8) and continued.

Second child: failed execve and original-image recovery
------------------------------------------------------
PID 1 created distinct child PID 22 with clone flags 17 and waited while the
new child was runnable. PID 22 wrote its pre-exec marker, then issued syscall
221 for /bin/riscv29-missing with argv
["/bin/riscv29-missing", "expect-ENOENT"] and envp
["GUIDEXOS_RISCV29_FAILURE=present"]. The syscall trace recorded the mapped
pathname and arguments for PID 22. The Linux kernel trace recorded
getname_flags, do_open_execat, and two lookup_fast events for the same task
between the execve ECALL and its return. No ELF loading, begin_new_exec, or
start_thread event occurred for the failed call.

Linux returned -2 at the next instruction 0x10364. The resumed raw instruction
0xffe00293 matches the independent /init ELF. PID 22 retained its task pointer,
PID, parent PID 1, SP 0x3fc4b8fb40, TP 0, and SATP 0x8000000000082483 across
the failure. The guest performed explicit stack store/load/restore operations
on its original stack, rechecked getpid/getppid, and wrote its recovery marker.
The run therefore proves that the missing-path execve was a genuine Linux
-ENOENT return and that the same process continued in the original image.

The second-child sentinel began as 0x29aabbcc. PID 22 wrote the private value
0x29998877, triggering an observed Sv39 copy-on-write store fault at PC
0x10310 for address 0x11008. The child's physical page separated from the
parent; after failed execve the child's value remained 0x29998877 and PID 1
still read 0x29aabbcc. The failed execve did not replace the address space or
erase the child's private data.

PID 22 exited with code 43 through Linux do_exit. PID 1's second wait4
returned PID 22 and copied status 11008 (43 << 8) to guest memory. A subsequent
wait4(-1, ..., WNOHANG) returned -10 (-ECHILD). PID 1 wrote the both-children
collected marker and remained alive. All eight R29 user markers were matched
to guest write syscalls and UART0 provenance; newline expansion accounts for
the one extra UART byte per marker.
