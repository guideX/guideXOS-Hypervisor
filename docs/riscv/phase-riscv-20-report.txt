Trap-accounting audit and correction
------------------------------------
RISCV-19's old trapDepth diagnostic incremented on trap transitions and
decremented on any MRET or SRET. It did not bind a handler invocation to its
architectural trap target, return privilege, and matching LIFO frame. It
could therefore count S-mode Linux exception handling as generic trap work,
retain stale depth across redirected or nested cases, and label cumulative
completed handlers as one long-running handler. Its 250,001 count was not an
accurate M-mode OpenSBI instruction total.

The RISCV-20 tracker records pre/post privilege, trap origin and target,
cause, return instruction, return target, resumption, and SBI registers. A
handler frame starts at an observed trap target and closes only on a matching
MRET/SRET from that active privilege. Handler instructions are charged to
the executing privilege. Linux S-mode handler work is separated from normal
S-mode execution. An unpaired or ambiguous lifetime is marked uncertain.
The expected Sv39 physical-alias redirect is recorded as a trap transition,
not as a new handler lifetime.

The tracker has bounded capacities: 8,192 retained trap events, 64 nested
handler frames, and a 32-PC per-event handler prefix. The continuation keeps
separate limits of 20,000,000 total retirements, 4,000,000 M-mode
instructions, 3,000,000 M-mode handler instructions, 1,000,000 S-mode
handler instructions, 200,000 per handler invocation, and 8,192 repeated
architectural states.

An initial corrected run stopped at 17,048,722 retirements when the original
4,096-event trace cap was reached. Its event stream showed repeated load and
store address-misaligned traps inside Linux's pinned
__riscv_copy_words_unaligned routine, with each OpenSBI M-mode handler
returning. This is Linux's boot-time unaligned-access probe, which
intentionally issues word-sized operations at unaligned addresses. OpenSBI
v1.8.1's sbi_trap_handler dispatches causes 4/6 to its misaligned load/store
emulators; the emulators perform byte accesses and advance mepc after a
successful operation. The events were expected firmware work, not an
unsupported instruction or nonprogress loop. The 4,096-event frontier was
preserved separately, and the bounded diagnostic capacity was raised to
8,192 based on this observed forward progress.

Final trap accounting at the 20-million cap: 4,851 non-retiring trap
transitions; 4,850 handler entries and 4,850 matching returns; zero active
frames; maximum nesting depth 2; largest individual handler 4,355 retired
instructions; no uncertain lifetimes, unmatched returns, or dropped events.
The events comprise 2,017 misaligned loads, 2,016 misaligned stores, 419
S-mode ECALLs, 199 machine timer interrupts, 199 supervisor timer interrupts,
and the one expected Sv39 alias page fault.

OpenSBI ECALL boundary
---------------------
The ECALL at the prior RISCV-19 mepc, 0xffffffff8000a56c, is inside the
pinned Linux function __sbi_ecall. It is a genuine 32-bit ECALL instruction
(0x00000073). The observed TIME calls use EID 0x54494D45 and FID 0. Arguments
a1-a5 are zero; a0 contains either the SBI timer-disable sentinel
0xffffffffffffffff or a requested deadline. Across the final run, all 419
SBI calls returned with SBI error a0=0. The 401 TIME calls also returned
a1=0; the 18 SBI Base calls returned version and extension-probe values in
a1. The repeated TIME calls had guest retirements between calls.

The dynamic event records the M-mode entry PC 0x80000448 (_trap_handler),
and the MRET at 0x800005d8 resumes Linux at 0xffffffff8000a570. The event
artifact stores the first 32 observed M-mode handler PCs and marks the path
truncated. The pinned fw_jump.elf symbol table identifies
sbi_trap_handler at 0x80019134 and sbi_ecall_handler at 0x8000f8e8; the
pinned OpenSBI source routes CAUSE_SUPERVISOR_ECALL to sbi_ecall_handler.
Thus the repeated calls are successful firmware services, not an error or
stuck ECALL. The host SBI provider remains absent.
