page fault at 0x80200098 (cause 12) was a non-handler transition used by the

handler loop.

The old frontier's PC 0xffffffff800a5cd0 is the `jalr x0,0(x1)` return at the
end of `tick_program_event`; x1 was 0xffffffff80095000, the return address in
`hrtimer_interrupt`. The authenticated dynamic call-site trace shows the
`hrtimer_interrupt` call at 0xffffffff80094ffc and a second caller,
`retrigger_next_event.constprop.0`, at 0xffffffff80094864. Both instructions
were read from guest memory and are `jal ra` calls into
tick_program_event at 0xffffffff800a5c70. The old stop was therefore on a
normal return path into the high-resolution timer interrupt routine.

Pinned Linux v6.12 timer source was checked in `kernel/time/tick-oneshot.c`,
`kernel/time/hrtimer.c`, and `kernel/time/clockevents.c`. The tick path can
stop a timer for KTIME_MAX and delegates event programming to the clockevent
device; a past deadline may return -ETIME and the high-resolution handler has
bounded retry behavior. The captured guest made no already-expired deadline
request, so no repeated immediate-expiration behavior was observed. Relevant
pinned source links:

SBI provider was present. The 10 MHz virtual timebase advances one tick per
retired guest instruction in this harness.

TIME deadline behavior:
- 701 calls deliberately requested UINT64_MAX to disable the event.
- 700 calls installed a future deadline.
- Zero deadlines were already expired when requested; zero active deadlines
  decreased; all 1,401 calls returned and resumed.
- 699 finite requests were followed by MTIP/cause 7 and then a supervisor
  timer interrupt (STIP/cause 5). The final finite request remained pending
  at the cap.
- Guest retirement between recurring TIME requests ranged from 769 to 57,104
  instructions (median 3,890); future-deadline requests ranged from 782 to
  4,201 (median 3,198).
